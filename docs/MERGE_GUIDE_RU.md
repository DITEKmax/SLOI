# Слияние доработки SLOI с локальным проектом

Эта поставка подготовлена из предоставленного `SLOI-main(1).zip`. Она не подтверждает, что локальный checkout или текущая ветка GitHub совпадает с этим архивом. Версия приложения не повышается. Доработка сохраняет ASR-модели и настройки распознавания; изменения касаются интерфейса, браузерного добавления файлов, выбора аудиодорожки и связанных проверок.

## Что находится в общем архиве

| Путь | Назначение |
|---|---|
| `SLOI/` | Полный снимок исходников и собранного интерфейса после доработки |
| `PATCH/` | Новые и изменённые код, сборка frontend, базовые настройки, документация и тесты с путями относительно корня; снимки и манифест полной поставки находятся в SLOI/ |
| `delivery/changes.json` | Список изменений и SHA-256 исходных/новых файлов |
| `delivery/changes.patch` | Текстовый diff для проверки и разрешения конфликтов |
| `delivery/SLOI_UX_Validation_RU.md` | Отчёт об изменениях и выполненных проверках |
| `SLOI/validation/` | Снимки интерфейса и материалы проверок |

Для существующей установки используйте проверяемое слияние файлов из `PATCH/`. Не заменяйте локальную папку целиком каталогом `SLOI/`. Не запускайте `update.bat` на этом общем архиве или на `PATCH/`: штатный updater рассчитан на другой формат релизного ZIP и может выполнять установку окружений.

## Порядок действий для локального агента

1. Определите корень существующей установки и checkout. Если есть Git, изучите `git status` и локальные изменения. Распакуйте поставку в отдельную папку рядом, без наложения на работающий проект.
2. Дайте активной записи завершиться либо остановите её по согласованному с пользователем сценарию. Остановите backend через `Ctrl+C` в его консоли и убедитесь, что worker завершён. Закрытия вкладки браузера недостаточно. Не обновляйте код при работающей очереди.
3. Создайте резервную копию текущего кода, локальных изменений, `config/app.yaml`, `runtime/active.json` и всей `data/` после остановки backend. Сохраните также имеющиеся `state.db-wal`/`state.db-shm`, если они остались. Разместите резервную копию вне папки, на которую будет накладываться обновление. Не удаляйте локальные модели, окружения или шрифты.
4. Прочитайте `delivery/changes.json`. В каждой записи массива `files` используйте `path`, `status`, `before_sha256` и `after_sha256`. Проверьте SHA-256 самого файла поставки из `PATCH/<path>` по `after_sha256`. Не применяйте файл с несовпадающим хешем.
5. Сравните текущий локальный файл с исходным и новым хешами по таблице ниже. Разрешите все конфликты до наложения файлов. Не предполагайте совпадение с `main` только по имени архива или ветки.
6. Перенесите только проверенные новые/изменённые файлы из `PATCH/` в корень локального проекта с сохранением относительных путей. Если локальные изменения отсутствуют и исходные хеши совпадают, разрешено прямое копирование этих файлов. Конфликтующие файлы слейте вручную, используя diff и локальную историю. Не удаляйте файлы, отсутствующие в `PATCH/`.
7. Убедитесь, что собранный `frontend/dist` соответствует применённым исходникам. Поставка уже содержит сборку; для обычного наложения и запуска Node.js не требуется. Если разрешение локального конфликта меняет TypeScript, Vue-шаблон или стили сверх поставки, пересоберите frontend существующим процессом разработки (`npm run build` из `frontend`) и проверьте новую сборку.
8. Выполните доступные проверки в остановленной установке, затем запустите `start.bat` и пройдите сценарий приёмки ниже. Сохраните результаты проверки и список разрешённых конфликтов.

### Как обрабатывать хеши

| Состояние | Действие |
|---|---|
| `modified`, локальный SHA-256 равен `before_sha256` | Можно наложить файл поставки |
| Локальный SHA-256 уже равен `after_sha256` | Файл уже применён; повторная замена не нужна |
| `modified`, локальный файл имеет другой хеш или отсутствует | Конфликт: изучить локальную историю и выполнить слияние |
| `added`, `before_sha256` равен `null`, локального файла нет | Можно добавить файл |
| `added`, одноимённый локальный файл уже существует и отличается | Конфликт: не затирать существующий файл |

В PowerShell отдельный хеш можно проверить командой:

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath 'D:\SLOI\sloi\app.py'
```

Сравнивайте шестнадцатеричные хеши без учёта регистра. `changes.patch` помогает изучить изменения; не применяйте его поверх уже наложенного `PATCH/` вторым проходом. Если выбран вариант применения текстового diff через Git, сначала выполните `git apply --check`, разберите конфликты и отдельно проверьте доставку собранных файлов и всех новых файлов по `changes.json`.

## Что нельзя перезаписывать или очищать

Сохраняйте локальные `config/app.yaml`, `runtime/`, `models/`, `data/`, `logs/`, `frontend/dist/fonts/` и установленные Python-окружения. В частности, не заменяйте `runtime/active.json`, SQLite с очередью/preferences, `data/results` или браузерный кэш `runtime/uploads` файлами из другой установки.

В `config/defaults.yaml` добавлены базовые ограничения браузерного переноса. Этот файл входит в изменения кода и может быть слит по исходным хешам. Пользовательские переопределения остаются в существующем `config/app.yaml`; не заменяйте его значениями defaults и не переносите в него все значения автоматически.

Новых зависимостей приложения в этой доработке нет. Не запускайте `install.bat`, не переустанавливайте модели и не создавайте новые окружения только ради применения этих изменений. Шрифты и установленные окружения используются существующие.

## Проверки после слияния

Используйте Python текущего core-окружения, указанный в `runtime/active.json`. Пример из корня проекта:

```powershell
$sloiMergeRoot = (Get-Location).Path
$sloiMergeActive = Get-Content -LiteralPath '.\runtime\active.json' -Raw -Encoding UTF8 | ConvertFrom-Json
$sloiMergePython = Join-Path $sloiMergeRoot $sloiMergeActive.environments.core
& $sloiMergePython -m compileall -q sloi
& $sloiMergePython -m pytest -q
```

`pytest` и его тестовые зависимости должны уже быть доступны в выбранном окружении разработки; они не нужны для обычного запуска приложения. Если их нет, зафиксируйте, что тесты не запускались в установленном core, и используйте отдельное существующее окружение тестирования с зависимостями `requirements/test.txt` и доступным FFmpeg. Не выдавайте отсутствие тестовой среды за успешную проверку.

После `start.bat` обновите страницу браузера, чтобы загрузился новый `frontend/dist`. Проверьте:

1. Прямой drop аудио/видео добавляет запись без второго системного выбора. Прогресс переноса виден; после него запись находится в очереди. Отмена переноса не удаляет ранее добавленные записи.
2. «Добавить без копирования» → «Выбрать через Windows» регистрирует исходник без медиа-копии. Отдельная зона Windows принимает drop. Эти проверки выполняются на Windows.
3. Выбор модели/языка новых файлов сохраняется после обновления страницы, а настройки существующих заданий остаются индивидуальными. Неустановленные модели недоступны для выбора.
4. Порядок ожидающих заданий меняется стрелками и перетаскиванием. Выбранная запись и текущая обработка различимы. Пауза после текущей и отмена дают ожидаемое состояние очереди.
5. Многодорожечное видео позволяет выбрать дорожку до запуска. Нужный индекс записывается в MD. Обычное видео продолжает использовать default-дорожку либо первую аудиодорожку.
6. Готовый текст открывается, копируется и скачивается. Удаление готовой строки сохраняет MD на диске. Браузерная медиа-копия освобождается после успеха, если её не использует другое незавершённое задание; ошибки/отмена сохраняют возможность повтора.
7. После завершения переноса закрытие вкладки не останавливает распознавание. Повторное открытие показывает состояние backend. Проверьте три темы, узкое окно и системный reduced motion.

Синтетические проверки FFmpeg подтверждают путь и формат аудио, а тестовые ASR-ответы — работу конвейера. Реальную точность и производительность моделей на Windows/GPU проверяйте собственной записью; облачный отчёт этого не заменяет.

## Откат

Остановите backend. Восстановите код и собранный frontend из резервной копии, сохраняя установленные модели/окружения/шрифты. Не возвращайте старую БД поверх новых готовых результатов без проверки: отдельно сопоставьте очередь, MD и браузерные копии. Если после обновления новых заданий и результатов не было, можно восстановить согласованную резервную копию `data/` и `config/app.yaml`, созданную после остановки приложения.
